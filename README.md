# ember

`ember` — маленький віртуальний комп'ютер на C++17: 4 КБ пам'яті, процесор із регістрами `A`, `B`, `H`, `SP`, `PC` і прапорцями `Z N C`, стек, екран 64×32 у пам'яті й асемблер, який перетворює текст `.asm` на байти.

## Як це влаштовано

```txt
 programs/fib.asm
        │  текст
        ▼
 ┌──────────────┐   список токенів   ┌──────────────┐  байти   ┌──────────────┐
 │ lexer        │ ─────────────────▶ │ assembler    │ ───────▶ │ Memory 4 КБ  │
 │ src/asm/     │  Ident Number ...  │ два проходи, │          │ 0x000–0xFFF  │
 └──────────────┘                    │ мітки        │          └──────┬───────┘
                                     └──────────────┘                 │ step / run
                                                                      ▼
                                     ┌──────────────┐  OUT/OUTN ┌──────────────┐
                                     │ екран 64×32  │ ◀──SHOW── │ CPU          │──▶ термінал
                                     │ VRAM 0xA00   │           │ A B H SP PC  │
                                     └──────────────┘           └──────────────┘
```

## Збірка й запуск

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
./build/ember programs/fib.asm
```

`./build/ember` без аргументів відкриває REPL (`help` — список команд). Debug-збірка вмикає AddressSanitizer і UndefinedBehaviorSanitizer (на Linux/macOS).

```txt
$ ./build/ember programs/hello.asm
HELLO
stopped after 2 steps

$ ./build/ember programs/search.asm
3
stopped after 38 steps

$ ./build/ember programs/fib.asm
8
stopped after 296 steps
```

## Програми

| Файл | Що робить |
|---|---|
| `programs/hello.asm` | `OUTS` рядка `HELLO`, покладеного в регіон даних через `DB` |
| `programs/search.asm` | лінійний пошук `0x41` у 8 байтах, друкує індекс або `-` |
| `programs/fib.asm` | рекурсивний Фібоначчі на `CALL`/`RET`: `fib(6) = 8` |

## Конвенція виклику

- Аргумент передається в `A`, результат повертається в `A`.
- `B` і `H` функція може зіпсувати. Якщо вони потрібні після `CALL`, той, хто викликає, сам робить `PUSH` до виклику й `POP` після.
- Усе, що функція кладе на стек для себе, вона знімає до `RET`.

## Мова `.asm`

```txt
мітка:  МНЕМОНІКА операнд, операнд   ; коментар
```

Операнди: `A`, `B`, `H`, число (`65`, `0x41`, `0b01000001`), мітка, `[адреса]`, `[мітка]`, `[H]`. Помилки повідомляються з номером рядка й зупиняють збірку:

```txt
$ ./build/ember bad.asm
bad.asm: line 3: bad number '0xGG'
```

## Обмеження

- Без макросів і без виразів в операндах (`2+3` не можна).
- Одна інструкція на рядок.
- Немає рядкових літералів: рядок пишеться через `DB` кодами символів.
- Необов'язкові інструкції ISA `JC`, `JNC`, `UNPLOT`, `PUSH H`, `POP H`, `ALLOC` не реалізовані.

## Що здивувало за вісім лаб

Найбільше здивувало, що «програма» і «дані» — це буквально ті самі байти в тій самій пам'яті. Екран виявився не окремим пристроєм, а 256 байтами, які можна засвітити звичайним `STORE`. Рекурсія — це просто `CALL`, адреса повернення і збережене `n` на стеку. А асемблер, який здавався найскладнішою частиною, на ділі просто рахує розміри інструкцій у двох проходах. Після цього шістнадцятковий дамп читається майже як текст.

## Розміри типів (`sizeof`)

| Тип | `sizeof` |
|---|---|
| `char` | 1 |

| `std::uint16_t` | 2 |

| `float` | 4 |
| `double` | 8 |
| `void*` | 8 |

## Чому комірка — `std::uint8_t`, а не `int`

Комірка `ember` має бути рівно одним байтом на будь-якій машині. Розмір `int` стандарт не фіксує, а `std::uint8_t` — це завжди 8 бітів. До того ж він беззнаковий: переповнення беззнакового типу визначене і загортається (255 + 1 = 0). Знакове переповнення — це UB.

## Notes §§1–4 своїми словами

1. **sizeof.** Розміри типів залежать від платформи й компілятора. Наприклад, `long` на Linux має 8 байтів, а на Windows — 4. Однаковими гарантовано є лише типи фіксованої ширини з `<cstdint>`.
2. **Переповнення.** Беззнакова арифметика за стандартом іде за модулем 2^n, тому загортання визначене. Для знакових типів стандарт нічого не обіцяє, і компілятор має право вважати, що переповнення не буває.
3. **Рухома кома.** `0.1` і `0.2` не мають точного двійкового запису, тому їхня сума трохи відрізняється від `0.3`.
4. **Символ — це число.** Байт `01000001` — це водночас `65`, `0x41` і `'A'`. Що саме ми побачимо, залежить від того, як ми його читаємо.

## M4 — досліди

### 1. Загортання байта і переповнення `int`

```txt
ember> set 0 255
ember> get 0
255  0xff  0b11111111  '.'
ember> inc 0
ember> get 0
0  0x00  0b00000000  '.'
```

`Byte` — це `std::uint8_t`, тож 255 + 1 загортається в 0, і це визначена поведінка.

Для порівняння, знаковий `int` (`INT_MAX + 1`), зібраний з UBSan:

```txt
ovf.cpp:3:43: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
-2147483648
```

Це невизначена поведінка, тому санітайзер видає звіт.

### 2. `0.1 + 0.2 == 0.3`

```txt
false
0.30000000000000004
```

`double` зберігає число у двійковому експоненційному записі. `0.1` і `0.2` у двійковій системі — нескінченні дроби, тому вони зберігаються з округленням. Сума цих наближень дає `0.30000000000000004`, а не те наближення, яким записано `0.3`. Тому `==` дає `false`. Дробові числа треба порівнювати з допуском або тримати величини в цілих.

### 3. C-рядок у пам'яті

```txt
ember> set 0 65
ember> set 1 66
ember> set 2 0
ember> dump
0000  41 42 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |AB..............|
```

У пам'яті лежить рядок `"AB"`, а нульовий байт за адресою 2 позначає його кінець.

### 4. Без `{}` у `Byte data[MEM_SIZE]{}`

```txt
ember> dump
0000  44 00 00 00 00 00 00 00 44 00 00 00 00 00 00 00  |D.......D.......|
0010  04 00 00 00 00 00 00 00 07 00 00 00 04 00 00 00  |................|
0020  60 fc 1f 00 00 00 00 00 60 0c 20 00 00 00 00 00  |`.......`. .....|
0030  60 0c 20 00 00 00 00 00 10 00 00 00 00 00 00 00  |`. .............|
```

Без `{}` масив не занулюється, і в ньому лежить сміття, яке залишилося на стеку. Читати його — UB. Після досліду дужки повернуто на місце.

## M1 — ALU, розібрані приклади

```txt
ember> alu add 200 100
result=44  Z=0 N=0 C=1
ember> alu and 12 10
result=8  Z=0 N=0 C=0
ember> alu shl 200
result=144  Z=0 N=1 C=1
ember> alu sub 5 10
result=251  Z=0 N=1 C=1
```

**200 + 100.** 300 не влазить у 8 бітів: 300 = 256 + 44. У байті лишається 44, а дев'ятий біт іде в `C`.

```txt
  11001000   (200)
+ 01100100   (100)
 ----------
1 00101100   (C=1, A=44)
```

**5 − 10.** Результат −5 загортається в 256 − 5 = 251 = `11111011`. Позика була (5 < 10), тому `C=1`. Старший біт дорівнює 1, тому `N=1`: якщо читати байт як `int8_t`, це −5 у доповняльному коді.

**AND 12, 10.** `00001100 & 00001010 = 00001000` = 8.

**SHL 200.** `11001000 << 1`: старша одиниця виїжджає в `C`, лишається `10010000` = 144, і `N=1`.

## M2 — програма `ADD`, `HALT`

## M3 — трасування

Програма `[AND, HALT]`, `A=7`, `B=1`:

| PC | mem[PC] | Інструкція | A | Z N C |
|---|---|---|---|---|
| 0000 | `12` | `AND A, B` | 1 | 0 0 0 |
| 0001 | `00` | `HALT` | 1 | 0 0 0 |

Своя програма `[SHL, SHL, INC, HALT]`, `A=96`: зсуваємо, поки не з'явиться перенесення.

```txt
ember> reg a 96
ember> set 0 0x16
ember> set 1 0x16
ember> set 2 0x18
ember> set 3 0x00
ember> regs
PC=0000  A=96  B=1  Z=0 N=0 C=0
ember> step
ember> regs
PC=0001  A=192  B=1  Z=0 N=1 C=0
ember> step
ember> regs
PC=0002  A=128  B=1  Z=0 N=1 C=1
ember> step
ember> regs
PC=0003  A=129  B=1  Z=0 N=1 C=1
ember> step
ember> regs
PC=0004  A=129  B=1  Z=0 N=1 C=1  halted
```

| PC | mem[PC] | Інструкція | A | Z N C |
|---|---|---|---|---|
| 0000 | `16` | `SHL A` | 192 (`11000000`) | 0 1 0 |
| 0001 | `16` | `SHL A` | 128 (`10000000`) | 0 1 1 |
| 0002 | `18` | `INC A` | 129 (`10000001`) | 0 1 1 |
| 0003 | `00` | `HALT` | 129 | 0 1 1 |

`INC` не чіпає `C` (за ISA він змінює лише `Z` і `N`), тому `C=1` після другого `SHL` лишився.

## M4 — розбір опкода маскою і зсувом

`decode()` у `cpu.cpp` ділить опкод на групу й індекс:

```cpp
d.group = (Byte)((op >> 4) & 0x0F);
d.index = (Byte)(op & 0x0F);
```

`step()` спочатку розводить `switch` за групою (`0x0` — керування, `0x1` — ALU), а вже всередині групи вибирає інструкцію.

## Баг із пріоритетом операцій

`==` зв'язує тісніше за `&`, тому `(op >> 4) & 0x0F == 1` — це `(op >> 4) & (0x0F == 1)`, тобто `(op >> 4) & 0` = 0 для будь-якого `op`.

З `-Wall -Werror` компілятор не пропускає такий код:

```txt
prec.cpp:5:69: error: suggest parentheses around comparison in operand of '&' [-Werror=parentheses]
```

Без `-Werror`, для `op = 0x12`:

```txt
(op >> 4) & 0x0F == 1   -> 0
((op >> 4) & 0x0F) == 1 -> 1
```

Якщо інструкція за адресою `PC` не вміщується в пам'ять (наприклад, 3-байтовий `LOAD` на `0xFFF`), `step` друкує помилку і зупиняє процесор.

## M1 — порядок байтів

`set16` — дзеркало `get16`: молодший байт `value & 0xFF` іде за адресою `addr`, старший `(value >> 8) & 0xFF` — за `addr + 1`.

```txt

ember> dump
```

`0x1234` лягло як `34 12`: молодший байт уперед (little-endian), як вимагає ISA.uk.md §4.

## M3 — дані за абсолютною адресою

## M4 — вказівник хоста проти адреси гостя

`CPU` тримає `Memory* mem` — вказівник **хоста**: це адреса всієї коробки в пам'яті нашого процесу C++. Він потрібен лише C++-коду, щоб знайти масив `data`. А `pc` і `h` — це адреси **гостя**: звичайні числа `0..4095`, індекси в `data`. Програма всередині `ember` бачить і змінює саме їх: `H` можна покласти в пам'ять, надрукувати, збільшити `INCH`. Вони однакові при кожному запуску і на будь-якій машині. Вказівник хоста (`Byte*` усередину `data`) гостю нічого не каже: це 8-байтова адреса процесу, вона щоразу інша, і в 16-бітний регістр вона навіть не влазить. Якщо змішати їх, наприклад записати вказівник хоста в пам'ять `ember` чи тримати `PC` як `Byte*`, програма-гість отримає число, яке після перезапуску або перевиділення пам'яті вказує в нікуди. До того ж `Byte*` можна збільшити за межі масиву, і ніхто цього не помітить. Індекс `uint16_t` ми перевіряємо порівнянням з `MEM_SIZE`, тому `step` ловить вихід за межу до того, як він станеться.

### Навмисний вихід за межу

Тимчасова програма пише на один байт за кінець масиву:

```cpp
Memory mem;
mem.data[MEM_SIZE] = 1;
```

Звіт ASan (головне):

```txt
==288==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7fdc11001020 at pc 0x55fd6c7be432 bp 0x7ffed83fbe40 sp 0x7ffed83fbe30
WRITE of size 1 at 0x7fdc11001020 thread T0
    #0 0x55fd6c7be431 in main oob.cpp:4
...
  This frame has 1 object(s):
    [32, 4128) 'mem' (line 3) <== Memory access at offset 4128 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow oob.cpp:4 in main
```

Три рядки, які мають значення:
1. `stack-buffer-overflow` і `WRITE of size 1` — це запис одного байта за межу масиву на стеку.
2. `#0 ... in main oob.cpp:4` — місце, де це сталося.
3. `'mem' ... overflows this variable` — яку саме змінну переповнено: `mem` займає байти `[32, 4128)`, а запис пішов на 4128.

UBSan окремо повідомив `index 4096 out of bounds for type 'unsigned char [4096]'`.

**Виправлення:** доступ до пам'яті йде тільки через `mem_set`/`mem_get`, які перевіряють `addr >= MEM_SIZE` до запису. `mem_set(mem, MEM_SIZE, 1)` повертає `false` і нічого не пише. Тимчасову програму видалено.

# Lab 04 — форма керування: стрибки, цикли, пошук

## Нові команди

| Команда | Що робить |
|---|---|
| `run` | тепер з лімітом кроків і підсумком: `stopped after N steps` |
| `find <lo> <hi> <byte>` | перша адреса в `[lo, hi)`, де лежить `byte`, або `not found` |

## Реалізовані рядки ISA.uk.md

| Опкод | Мнемоніка | Розмір | Прапорці |
|---|---|---|---|
| `0x1A` | `CMP A, B` | 1 | Z N C |
| `0x2D` | `HLOW` | 1 | — |
| `0x30` | `JMP addr16` | 3 | — |
| `0x31` | `JZ addr16` | 3 | — |
| `0x32` | `JNZ addr16` | 3 | — |

`CMP` рахує `A - B` тією самою функцією `alu_sub`, але результат викидає: змінюються лише прапорці. `HLOW` (`A = H & 0xFF`) потрібен програмі пошуку, щоб надрукувати індекс.

## M1 — повний декодер

`step` розводить опкод за групою (`(op >> 4) & 0x0F`), а в кожній групі є окремий `switch`, де кожен відомий опкод має свій `case`. `default` кожної групи (і `default` самого розбору груп) повертає «невідомо», і тоді `step` друкує помилку й зупиняє машину. Тихого `NOP` для сміття більше немає:

```txt
ember> set 0 0x01
ember> set 1 0x77
ember> run
error: unknown opcode 0x77 at PC=0x0001
stopped after 2 steps
```

## M2 — стрибки і ліміт кроків

`step` спершу рахує `next = PC + розмір`. Стрибок, що спрацював, переписує `next` на адресу з операнда, і `PC = next`. Тому до адреси стрибка розмір інструкції не додається. Стрибок, що не спрацював, лишає `next = PC + 3`.

**Ліміт кроків:** `run` виконує не більше `RUN_STEP_LIMIT = 100000` кроків (константа в `cpu.hpp`). Коли ліміт спрацьовує, машина не зупиняється назавжди, а стає на паузу: `run` або `step` можна викликати знову. Друкується:

```txt
ember> set 0 0x30
ember> set 1 0
ember> set 2 0
ember> run

step limit 100000 reached, machine paused at PC=0x0000
```

(`JMP 0x0000` на адресі 0 — нескінченний цикл.)

## M3 — зворотний відлік

```txt
адр.  байти       текст
0000  20 03       LOADI A, 3
0002  03          loop:  OUTN
0003  19                 DEC A
0004  32 02 00           JNZ loop
0007  00                 HALT
```

```txt
ember> run
3 2 1
stopped after 11 steps
ember> regs
PC=0008  H=0000  A=0  B=0  Z=1 N=0 C=0  halted
```

Трасування (стан **після** кожного `step`):

| Крок | PC до | Інструкція | PC після | A | Z |
|---|---|---|---|---|---|
| 1 | 0000 | `LOADI A, 3` | 0002 | 3 | 0 |
| 2 | 0002 | `OUTN` → друк `3` | 0003 | 3 | 0 |
| 3 | 0003 | `DEC A` | 0004 | 2 | 0 |
| 4 | 0004 | `JNZ 0002` — стрибок | 0002 | 2 | 0 |
| 5 | 0002 | `OUTN` → друк `2` | 0003 | 2 | 0 |
| 6 | 0003 | `DEC A` | 0004 | 1 | 0 |
| 7 | 0004 | `JNZ 0002` — стрибок | 0002 | 1 | 0 |
| 8 | 0002 | `OUTN` → друк `1` | 0003 | 1 | 0 |
| 9 | 0003 | `DEC A` | 0004 | 0 | 1 |
| 10 | 0004 | `JNZ 0002` — не стрибає | 0007 | 0 | 1 |
| 11 | 0007 | `HALT` | 0008 | 0 | 1 |

Той самий цикл на C++:

```cpp
Byte a = 3;                      // LOADI A, 3
do {
    std::cout << (int)a << ' ';  // OUTN
    a = a - 1;                   // DEC A (виставляє Z, коли a == 0)
} while (a != 0);                // JNZ loop
                                 // HALT
```

Перевірка стоїть **після** тіла циклу (`JNZ` наприкінці), тому це форма `do … while`: тіло виконується хоча б раз. Звичайний `while (a != 0) { ... }` дав би той самий вивід для `a = 3`, але в байтах мав би перевірку на початку і `JMP` назад наприкінці.

## M4 — лінійний пошук, двічі

### На C++: команда `find`

```cpp
std::uint16_t find(const Memory& mem, std::uint16_t lo, std::uint16_t hi, Byte needle) {
    for (std::uint16_t i = lo; i < hi; ++i) {
        if (mem_get(mem, i) == needle) return i;
    }
    return hi;
}
```

```txt
ember> set 0x800 7
ember> set 0x803 0x41
ember> set 0x806 0x41
ember> find 0x800 0x808 0x41
found at 2051 (0x803)
ember> find 0x800 0x803 0x41
not found in [2048, 2051)
```

Промах — це повернене значення `hi`: такої адреси в діапазоні `[lo, hi)` бути не може.

### Усередині `ember`

Шукає `0x41` у восьми байтах `0x800`–`0x807`. Друкує індекс (0–7) через `OUTN`, а при промаху — символ `-`.

**Як цикл дізнається про `hi`:** після `INCH` молодший байт `H` (через `HLOW`) порівнюється з `0x08`. Ділянка починається з `0x0800`, молодший байт якої дорівнює `00`, тому `HLOW` одразу дає індекс, а `0x08` — це `hi`. Через те що `B` потрібен для порівняння з межею, на початку кожного кроку в `B` знову кладеться `0x41`.

```txt
адр.  байти       текст
0000  28 00 08          LOADH H, 0x0800     ; i = lo
0003  29          loop: LOAD  A, [H]        ; A = mem[i]
0004  21 41             LOADI B, 0x41       ; що шукаємо
0006  1A                CMP   A, B
0007  31 15 00          JZ    found         ; mem[i] == 0x41
000A  2B                INCH                ; ++i
000B  2D                HLOW                ; A = i
000C  21 08             LOADI B, 0x08       ; hi
000E  1A                CMP   A, B
000F  31 18 00          JZ    notfound      ; i == hi
0012  30 03 00          JMP   loop
0015  2D          found:    HLOW            ; A = i
0016  03                    OUTN            ; надрукувати індекс
0017  00                    HALT
0018  20 2D       notfound: LOADI A, '-'
001A  02                    OUT             ; надрукувати '-'
001B  00                    HALT
```

Той самий пошук на C++ у тих самих кроках:

```cpp
std::uint16_t h = 0x0800;                       // LOADH H, 0x0800
while (true) {
    if (mem_get(mem, h) == 0x41) {              // LOAD A,[H] / CMP / JZ found
        std::cout << (h & 0xFF) << ' ';         // found: HLOW, OUTN
        break;
    }
    ++h;                                        // INCH
    if ((h & 0xFF) == 0x08) {                   // HLOW / CMP / JZ notfound
        std::cout << '-';                       // notfound: OUT
        break;
    }
}                                               // JMP loop
```

Набрати через `set`:

```txt
set 0 0x28   set 1 0x00   set 2 0x08   set 3 0x29   set 4 0x21   set 5 0x41
set 6 0x1A   set 7 0x31   set 8 0x15   set 9 0x00   set 10 0x2B  set 11 0x2D
set 12 0x21  set 13 0x08  set 14 0x1A  set 15 0x31  set 16 0x18  set 17 0x00
set 18 0x30  set 19 0x03  set 20 0x00  set 21 0x2D  set 22 0x03  set 23 0x00
set 24 0x20  set 25 0x2D  set 26 0x02  set 27 0x00
```

```txt
ember> dump
0000  28 00 08 29 21 41 1a 31 15 00 2b 2d 21 08 1a 31  |(..)!A.1..+-!..1|
0010  18 00 30 03 00 2d 03 00 20 2d 02 00 00 00 00 00  |..0..-.. -......|
```

Знайдено (дані `07 08 09 41 00 00 41 00` — береться перший збіг):

```txt
ember> run
3
stopped after 38 steps
ember> regs
PC=0018  H=0803  A=3  B=65  Z=1 N=0 C=0  halted
```

Не знайдено (`0x41` лежить на `0x808`, за межею ділянки):

```txt
ember> run
-
stopped after 83 steps
ember> regs
PC=001c  H=0808  A=45  B=8  Z=1 N=0 C=0  halted
```

Крайні випадки: `0x41` на `0x800` друкує `0`, на `0x807` — `7`.

## Реалізовані рядки ISA.uk.md

| Опкод | Мнемоніка | Розмір | Прапорці |
|---|---|---|---|
| `0x04` | `OUTS addr16` | 3 | — |
| `0x40` | `CLS` | 1 | — |
| `0x41` | `PLOT` | 1 | C |
| `0x43` | `SHOW` | 1 | — |

`PLOT` бере `x = A`, `y = B`. Якщо піксель за межами екрана, виставляє `C=1` і нічого не змінює, інакше `C=0`.

## Формула «байт і біт»

```txt
адреса байта = 0xA00 + y * 8 + (x / 8)
номер біта   = 7 - (x % 8)
засвітити:  mem[адреса] |= (1 << номер біта)
горить:     (mem[адреса] >> номер біта) & 1
```

Рядок екрана — 64 пікселі = 8 байтів, тому крок рядка 8. `x / 8` — який байт у рядку, `x % 8` — який біт у ньому. Біт 7 — найлівіший піксель, тому `7 -`. Приклад: піксель (13, 2) → байт `0xA00 + 16 + 1 = 0xA11`, біт `7 - 5 = 2`, тобто байт `0x04`.

Екран — це не окремий масив, а 256 байтів `mem.data[0xA00..0xAFF]` тієї самої пам'яті.

Байт `0x80` = `10000000`: горить лише біт 7, тобто найлівіший піксель першого байта першого рядка — лівий верхній кут.

- `0xA08` = `80` = `10000000`: рядок 1, пікселі x = 0..7, горить тільки x = 0 — ліва стінка рамки.
- `0xA0F` = `01` = `00000001`: рядок 1, пікселі x = 56..63, горить тільки x = 63 — права стінка.

## M4 — рядки: `OUTS`

`OUTS addr` друкує байти з `addr`, поки не трапиться `0`, але не більше 256 байтів і не далі кінця пам'яті.

```txt
ember> set 0x800 72
ember> set 0x801 69
ember> set 0x802 76
ember> set 0x803 76
ember> set 0x804 79
ember> set 0x805 0
ember> set 0 0x04
ember> set 1 0x00
ember> set 2 0x08
ember> set 3 0x00
ember> run
HELLO
stopped after 2 steps
```

Стеля: якщо покласти на `0x800` 300 байтів `*` без нуля в кінці, `OUTS 0x0800` друкує рівно 256 символів і зупиняється. Рядок на `0xFFE` без нуля друкується до кінця пам'яті і теж зупиняється.

`0xA11` → `0xA11 - 0xA00 = 17 = 2 * 8 + 1`: рядок `y = 2`, байт 1 (пікселі x = 8..15), значення `0x04` = біт 2 → `x = 8 + (7 - 2) = 13`. Знайшли саме той піксель, який засвітили.

### `sizeof` і вирівнювальні байти

Нова команда `layout` друкує розміри й зсуви полів (`offsetof`):


# Lab 07 — виклик і повернення: стек, CALL/RET, рекурсія

## Нові команди й інструкції

| Команда | Що робить |
|---|---|
| `stack` | друкує `SP` і до 8 верхніх байтів стека |
| `regs` | тепер друкує ще й `SP` |

| Опкод | Мнемоніка | Розмір | Прапорці |
|---|---|---|---|
| `0x1B` | `MUL A, B` | 1 | Z N C |
| `0x50` | `PUSH A` | 1 | — |
| `0x51` | `POP A` | 1 | — |
| `0x52` | `PUSH B` | 1 | — |
| `0x53` | `POP B` | 1 | — |
| `0x54` | `CALL addr16` | 3 | — |
| `0x55` | `RET` | 1 | — |

`MUL` множить у `unsigned`, кладе в `A` молодші 8 бітів добутку і виставляє `C`, якщо добуток більший за 255.

## M1 — `Stack` як абстрактний тип

```cpp
// stack.hpp
const std::uint16_t STACK_LO = 0xF00;
const std::uint16_t STACK_HI = 0xFFF;

struct Stack {
    std::uint16_t sp = STACK_HI;
};

bool push(Stack& s, Memory& mem, Byte value);
bool pop(Stack& s, const Memory& mem, Byte& out);
bool empty(const Stack& s);
bool full(const Stack& s);
std::uint16_t stack_pointer(const Stack& s);
void print_stack(const Stack& s, const Memory& mem);
```

Стек «порожній спадний»: `SP` вказує на наступний вільний байт. `push` пише в `mem[SP]` і зменшує `SP`, `pop` спершу збільшує `SP`, потім читає. Байти стека лежать у пам'яті `ember` (`0xF00`–`0xFFF`), а `CPU` тримає лише `Stack stack`. `cpu.cpp` викликає тільки `push`/`pop`/`stack_pointer` і ніде не чіпає `sp` напряму, тож представлення можна поміняти, не змінюючи `cpu.cpp`.

- **Переповнення:** `push` при `SP < 0xF00` повертає `false`.
- **Спустошення:** `pop` при `SP >= 0xFFF` повертає `false`.

В обох випадках `step` друкує повідомлення й зупиняє машину:

```txt
ember> set 0 0x51
ember> run
error: stack underflow at PC=0x0000, SP=0x0fff
stopped after 1 steps
```

`PUSH A` у нескінченному циклі (`PUSH A`, `JMP 0x0000`) — 256 вдалих `PUSH`, і на 257-му:

```txt
error: stack overflow at PC=0x0000, SP=0x0eff
stopped after 513 steps
```

## M2 — `CALL` / `RET` на один рівень

```txt
адр.  байти       текст
0000  20 41       LOADI A, 'A'
0002  54 06 00    CALL  printA
0005  00          HALT
0006  02          printA: OUT
0007  55                  RET
```

`CALL` на адресі `P` кладе `P + 3` — спершу молодший байт, потім старший — і ставить `PC = addr`. `RET` знімає спершу старший, потім молодший байт.

| Крок | Інструкція | PC після | SP після | Стек (`0xFFE`, `0xFFF`) |
|---|---|---|---|---|
| — | старт | 0000 | 0FFF | порожній |
| 1 | `LOADI A, 'A'` | 0002 | 0FFF | порожній |
| 2 | `CALL 0x0006` | 0006 | 0FFD | `00 05` |
| 3 | `OUT` → друк `A` | 0007 | 0FFD | `00 05` |
| 4 | `RET` | 0005 | 0FFF | порожній |
| 5 | `HALT` | 0006 | 0FFF | порожній |

```txt
ember> step
ember> regs
PC=0006  SP=0ffd  H=0000  A=65  B=0  Z=0 N=0 C=0
ember> stack
SP=0ffd  top: 0ffe=00 0fff=05
```

На стеку `0FFF = 05` (молодший байт, покладений першим) і `0FFE = 00` (старший), тобто адреса повернення `0x0005`.

**Чому `PC + 3`, а не адреса самого `CALL`:** `CALL` займає три байти (опкод і два байти адреси). Повертатися треба на **наступну** інструкцію, тобто на `HALT` за `0x0005`. Якби на стек клали `0x0002`, `RET` повернув би на той самий `CALL`, і програма викликала б `printA` знову й знову, поки стек не переповниться.

## Конвенція виклику (своїми словами)

- Функція отримує свій єдиний аргумент у регістрі `A` і віддає результат теж в `A`.
- Функція має право зіпсувати `B` і `H`. Якщо тому, хто викликає, вони потрібні після виклику, він сам робить `PUSH` перед `CALL` і `POP` після.
- Якщо самій функції треба щось зберегти на час свого виконання (як `fact` зберігає `n`), вона кладе це на стек сама і обов'язково знімає до `RET`. Інакше `RET` зніме не адресу повернення, а ці дані.

## M1 — лексер

- `0x` / `0X` → далі шістнадцяткові цифри;
- `0b` / `0B` → далі двійкові цифри;
- інакше десяткові цифри.

Число зіпсоване, якщо після префікса немає жодної цифри (`0x`) або одразу після цифр іде літера, цифра чи `_`, що не належить цій системі числення (`0xGG`, `12ab`, `0b102`). Тоді лексер повертає помилку з номером рядка, а список, який він встиг побудувати, звільняється.

### Список токенів

Токени — однозв'язний список: `lex` додає вузли в хвіст (`new Token`, `tail->next = t`), асемблер обходить його через `t = t->next`, а `destroy` проходить і робить `delete` кожному вузлу. Список, а не масив, бо довжина файлу наперед невідома. `destroy` викликається на всіх шляхах: після збірки, після `lex` і всередині `lex` при помилці. Debug-збірка з ASan/LSan на всіх трьох програмах і на всіх файлах з помилками нічого не повідомляє.

## M2 — асемблер у два проходи

1. **Розбір рядків.** Список токенів ріжеться на рядки (до `Newline`): необов'язкова мітка `ім'я:`, мнемоніка, операнди через кому.
2. **Прохід 1.** Лічильник адреси йде від `0`. Мітка запам'ятовує поточну адресу, кожна інструкція додає свій розмір, `ORG` переставляє лічильник, `DB` додає кількість байтів.
3. **Прохід 2.** Лічильник іде знову, і кожен рядок перетворюється на байти: опкод, `imm8` — один байт, адреса чи мітка — два байти, молодший уперед.

Розмір інструкції асемблер бере з тієї самої функції `instruction_size(Op)`, що й `step()`, тож розійтися вони не можуть. Форма кожної інструкції (мнемоніка + види операндів → опкод) лежить в одній таблиці `FORMS` в `assembler.cpp`.

Два проходи потрібні, бо `JZ found` стоїть **вище** за `found:`: на першому проході адреса `found` ще невідома, а розмір `JZ` (3 байти) відомий, тож адреси всіх міток можна порахувати до того, як видати хоч один байт.

Перевірка на повний оберт:

```txt
ember> asm rt.asm
0000  00              HALT
0001  30 23 01        JMP 0x0123
```

Помилки асемблера:

### `fib.asm`

```asm
; fib.asm — рекурсивний Фібоначчі. Друкує fib(6) = 8.
        LOADI A, 6
        CALL  fib
        OUTN
        HALT

; fib(n): аргумент в A, результат в A. Псує B.
fib:    LOADI B, 0
        CMP   A, B
        JZ    done              ; fib(0) = 0
        LOADI B, 1
        CMP   A, B
        JZ    done              ; fib(1) = 1
        PUSH  A                 ; зберегти n
        DEC   A
        CALL  fib               ; A = fib(n-1)
        POP   B                 ; B = n
        PUSH  A                 ; зберегти fib(n-1)
        MOV   A, B              ; A = n
        DEC   A
        DEC   A
        CALL  fib               ; A = fib(n-2)
        POP   B                 ; B = fib(n-1)
        ADD   A, B              ; A = fib(n-1) + fib(n-2)
done:   RET
```

`fib` дотримується конвенції: аргумент і результат в `A`, `B` псується. Тому `n` між двома рекурсивними викликами живе на стеку, а потім там само чекає `fib(n-1)`, поки рахується `fib(n-2)`.
