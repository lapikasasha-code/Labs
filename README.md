# ember — Lab 01: коробка байтів

`ember` — віртуальна пам'ять на 4096 байтів із prompt, у якому її можна читати, змінювати й друкувати.

## Збірка і запуск

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build
./build/ember
```

Збірка: C++17, `-Wall -Wextra -Werror`, на Debug увімкнені AddressSanitizer і UndefinedBehaviorSanitizer.

## Команди

| Команда | Що робить |
|---|---|
| `dump` | друкує всі 4096 байтів: адреса, hex, ASCII |
| `get <addr>` | показує один байт десятково, hex, двійково і символом |
| `set <addr> <val>` | записує байт (0..255, десятково або `0x`) |
| `inc <addr>` | додає 1 до байта (255 загортається в 0) |
| `help` | список команд |
| `quit` | вихід |

## M1 — збирається і запускається

```txt
ember 0.1 - 4096 bytes of memory you can see. Type `help`.
ember>
```

`main.cpp` у циклі читає рядок, бере перше слово як команду, і ланцюжок `else if` вирішує, що виконати: `quit`/`exit` — вихід, `help` — список, `dump` — дамп, `get` — показ байта, `set` — запис байта. Невідома команда потрапляє в останній `else` і друкує `unknown command`.

## M2 — після старту пам'ять порожня

```txt
ember> dump

0010  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
0020  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
```

## M3 — читання і запис байта

```txt
ember> set 0 65
ember> get 0
65  0x41  0b01000001  'A'
ember> set 5000 1
address 5000 is outside 0..4095
```

## Розміри типів (`sizeof`)

| Тип | `sizeof` |
|---|---|
| `char` | 1 |
| `std::uint8_t` | 1 |
| `std::uint16_t` | 2 |
| `int` | 4 |
| `unsigned` | 4 |
| `long` | 8 |
| `float` | 4 |
| `double` | 8 |
| `void*` | 8 |

## Чому комірка — `std::uint8_t`, а не `int`

Комірка `ember` має бути рівно одним байтом на будь-якій машині. Розмір `int` стандарт не фіксує, а `std::uint8_t` — це завжди 8 бітів. До того ж він беззнаковий: переповнення беззнакового типу визначене і загортається (255 + 1 = 0). Знакове переповнення — це UB.

## Notes §§1–4 своїми словами

1. **sizeof.** Розміри типів залежать від платформи й компілятора. Наприклад, `long` на Linux має 8 байтів, а на Windows — 4. Однаковими гарантовано є лише типи фіксованої ширини з `<cstdint>`.
2. **Переповнення.** Беззнакова арифметика за стандартом іде за модулем 2^n, тому загортання визначене. Для знакових типів стандарт нічого не обіцяє, і компілятор має право вважати, що переповнення не буває.
3. **Рухома кома.** `0.1` і `0.2` не мають точного двійкового запису, тому їхня сума трохи відрізняється від `0.3`.
4. **Символ — це число.** Байт `01000001` — це водночас `65`, `0x41` і `'A'`. Що саме ми побачимо, залежить від того, як ми його читаємо.

## M4 — досліди

### 1. Загортання байта і переповнення `int`

```txt
ember> set 0 255
ember> get 0
255  0xff  0b11111111  '.'
ember> inc 0
ember> get 0
0  0x00  0b00000000  '.'
```

`Byte` — це `std::uint8_t`, тож 255 + 1 загортається в 0, і це визначена поведінка.

Для порівняння, знаковий `int` (`INT_MAX + 1`), зібраний з UBSan:

```txt
ovf.cpp:3:43: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
-2147483648
```

Це невизначена поведінка, тому санітайзер видає звіт.

### 2. `0.1 + 0.2 == 0.3`

```txt
false
0.30000000000000004
```

`double` зберігає число у двійковому експоненційному записі. `0.1` і `0.2` у двійковій системі — нескінченні дроби, тому вони зберігаються з округленням. Сума цих наближень дає `0.30000000000000004`, а не те наближення, яким записано `0.3`. Тому `==` дає `false`. Дробові числа треба порівнювати з допуском або тримати величини в цілих.

### 3. C-рядок у пам'яті

```txt
ember> set 0 65
ember> set 1 66
ember> set 2 0
ember> dump
0000  41 42 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |AB..............|
```

У пам'яті лежить рядок `"AB"`, а нульовий байт за адресою 2 позначає його кінець.

### 4. Без `{}` у `Byte data[MEM_SIZE]{}`

```txt
ember> dump
0000  44 00 00 00 00 00 00 00 44 00 00 00 00 00 00 00  |D.......D.......|
0010  04 00 00 00 00 00 00 00 07 00 00 00 04 00 00 00  |................|
0020  60 fc 1f 00 00 00 00 00 60 0c 20 00 00 00 00 00  |`.......`. .....|
0030  60 0c 20 00 00 00 00 00 10 00 00 00 00 00 00 00  |`. .............|
```

Без `{}` масив не занулюється, і в ньому лежить сміття, яке залишилося на стеку. Читати його — UB. Після досліду дужки повернуто на місце.

# Lab 02 — біти не брешуть: ALU і процесор

## Нові команди

| Команда | Що робить |
|---|---|
| `reg <a\|b> <val>` | кладе значення в регістр `A` або `B` |
| `regs` | друкує `PC A B Z N C` |
| `step` | виконує одну інструкцію за адресою `PC` |
| `alu <op> <a> [b]` | виконує одну операцію ALU і друкує результат з прапорцями |

## Реалізовані рядки ISA.uk.md

| Опкод | Мнемоніка | Розмір | Прапорці |
|---|---|---|---|
| `0x00` | `HALT` | 1 | — |
| `0x01` | `NOP` | 1 | — |
| `0x10` | `ADD A, B` | 1 | Z N C |
| `0x11` | `SUB A, B` | 1 | Z N C |
| `0x12` | `AND A, B` | 1 | Z N, C=0 |
| `0x13` | `OR A, B` | 1 | Z N, C=0 |
| `0x14` | `XOR A, B` | 1 | Z N, C=0 |
| `0x15` | `NOT A` | 1 | Z N, C=0 |
| `0x16` | `SHL A` | 1 | Z N C |
| `0x17` | `SHR A` | 1 | Z N C |
| `0x18` | `INC A` | 1 | Z N |
| `0x19` | `DEC A` | 1 | Z N |

Власних розширень поки немає.

## M1 — ALU, розібрані приклади

```txt
ember> alu add 200 100
result=44  Z=0 N=0 C=1
ember> alu and 12 10
result=8  Z=0 N=0 C=0
ember> alu shl 200
result=144  Z=0 N=1 C=1
ember> alu sub 5 10
result=251  Z=0 N=1 C=1
```

**200 + 100.** 300 не влазить у 8 бітів: 300 = 256 + 44. У байті лишається 44, а дев'ятий біт іде в `C`.

```txt
  11001000   (200)
+ 01100100   (100)
 ----------
1 00101100   (C=1, A=44)
```

**5 − 10.** Результат −5 загортається в 256 − 5 = 251 = `11111011`. Позика була (5 < 10), тому `C=1`. Старший біт дорівнює 1, тому `N=1`: якщо читати байт як `int8_t`, це −5 у доповняльному коді.

**AND 12, 10.** `00001100 & 00001010 = 00001000` = 8.

**SHL 200.** `11001000 << 1`: старша одиниця виїжджає в `C`, лишається `10010000` = 144, і `N=1`.

## M2 — програма `ADD`, `HALT`

```txt
ember> reg a 200
ember> reg b 100
ember> set 0 0x10
ember> set 1 0x00
ember> regs
PC=0000  A=200  B=100  Z=0 N=0 C=0
ember> step
ember> regs
PC=0001  A=44  B=100  Z=0 N=0 C=1
ember> step
ember> regs
PC=0002  A=44  B=100  Z=0 N=0 C=1  halted
ember> step
halted
```

## M3 — трасування

Програма `[AND, HALT]`, `A=7`, `B=1`:

| PC | mem[PC] | Інструкція | A | Z N C |
|---|---|---|---|---|
| 0000 | `12` | `AND A, B` | 1 | 0 0 0 |
| 0001 | `00` | `HALT` | 1 | 0 0 0 |

Своя програма `[SHL, SHL, INC, HALT]`, `A=96`: зсуваємо, поки не з'явиться перенесення.

```txt
ember> reg a 96
ember> set 0 0x16
ember> set 1 0x16
ember> set 2 0x18
ember> set 3 0x00
ember> regs
PC=0000  A=96  B=1  Z=0 N=0 C=0
ember> step
ember> regs
PC=0001  A=192  B=1  Z=0 N=1 C=0
ember> step
ember> regs
PC=0002  A=128  B=1  Z=0 N=1 C=1
ember> step
ember> regs
PC=0003  A=129  B=1  Z=0 N=1 C=1
ember> step
ember> regs
PC=0004  A=129  B=1  Z=0 N=1 C=1  halted
```

| PC | mem[PC] | Інструкція | A | Z N C |
|---|---|---|---|---|
| 0000 | `16` | `SHL A` | 192 (`11000000`) | 0 1 0 |
| 0001 | `16` | `SHL A` | 128 (`10000000`) | 0 1 1 |
| 0002 | `18` | `INC A` | 129 (`10000001`) | 0 1 1 |
| 0003 | `00` | `HALT` | 129 | 0 1 1 |

`INC` не чіпає `C` (за ISA він змінює лише `Z` і `N`), тому `C=1` після другого `SHL` лишився.

## M4 — розбір опкода маскою і зсувом

`decode()` у `cpu.cpp` ділить опкод на групу й індекс:

```cpp
d.group = (Byte)((op >> 4) & 0x0F);
d.index = (Byte)(op & 0x0F);
```

`step()` спочатку розводить `switch` за групою (`0x0` — керування, `0x1` — ALU), а вже всередині групи вибирає інструкцію.

## Баг із пріоритетом операцій

`==` зв'язує тісніше за `&`, тому `(op >> 4) & 0x0F == 1` — це `(op >> 4) & (0x0F == 1)`, тобто `(op >> 4) & 0` = 0 для будь-якого `op`.

З `-Wall -Werror` компілятор не пропускає такий код:

```txt
prec.cpp:5:69: error: suggest parentheses around comparison in operand of '&' [-Werror=parentheses]
```

Без `-Werror`, для `op = 0x12`:

```txt
(op >> 4) & 0x0F == 1   -> 0
((op >> 4) & 0x0F) == 1 -> 1
```

# Lab 03 — адреси, а не імена: LOAD, STORE і регістр H

Якщо інструкція за адресою `PC` не вміщується в пам'ять (наприклад, 3-байтовий `LOAD` на `0xFFF`), `step` друкує помилку і зупиняє процесор.

## M1 — порядок байтів

`set16` — дзеркало `get16`: молодший байт `value & 0xFF` іде за адресою `addr`, старший `(value >> 8) & 0xFF` — за `addr + 1`.

```txt
ember> set16 0 0x1234
ember> dump
0000  34 12 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |4...............|
ember> set16 4095 1
address 4095 is outside 0..4094
```

`0x1234` лягло як `34 12`: молодший байт уперед (little-endian), як вимагає ISA.uk.md §4.

## M3 — дані за абсолютною адресою

Дані `ABC\0` на `0x800`, програма на `0x000`: `LOAD A, [0x0800]`, `OUT`, `HALT`.

```txt
ember> set 0x800 65
ember> set 0x801 66
ember> set 0x802 67
ember> set 0x803 0
ember> set 0 0x22
ember> set 1 0x00
ember> set 2 0x08
ember> set 3 0x02
ember> set 4 0x00
ember> run
A
ember> regs
PC=0005  H=0000  A=65  B=0  Z=0 N=0 C=0  halted
ember> dump
0000  22 00 08 02 00 00 00 00 00 00 00 00 00 00 00 00  |"...............|
...
0800  41 42 43 00 00 00 00 00 00 00 00 00 00 00 00 00  |ABC.............|
```

Адреса `0x0800` в інструкції записана як `00 08`, молодший байт уперед.

## M3 — те саме через `H`

Дані `65 66 0` на `0x800`. Програма: `LOADH H, 0x0800`, `LOAD A, [H]`, `OUT`, `INCH`, `LOAD A, [H]`, `OUT`, `HALT` = байти `28 00 08 29 02 2B 29 02 00`.

```txt
ember> regs
PC=0000  H=0000  A=0  B=0  Z=0 N=0 C=0
ember> step
ember> regs
PC=0003  H=0800  A=0  B=0  Z=0 N=0 C=0
ember> step
ember> regs
PC=0004  H=0800  A=65  B=0  Z=0 N=0 C=0
ember> step
A
ember> regs
PC=0005  H=0800  A=65  B=0  Z=0 N=0 C=0
ember> step
ember> regs
PC=0006  H=0801  A=65  B=0  Z=0 N=0 C=0
ember> step
ember> regs
PC=0007  H=0801  A=66  B=0  Z=0 N=0 C=0
ember> step
B
ember> regs
PC=0008  H=0801  A=66  B=0  Z=0 N=0 C=0
ember> step
ember> regs
PC=0009  H=0801  A=66  B=0  Z=0 N=0 C=0  halted
```

| PC | Байти | Інструкція | Що змінилось |
|---|---|---|---|
| 0000 | `28 00 08` | `LOADH H, 0x0800` | `H=0800`, `PC` +3 |
| 0003 | `29` | `LOAD A, [H]` | `A=65` (`'A'`) |
| 0004 | `02` | `OUT` | надруковано `A` |
| 0005 | `2B` | `INCH` | `H=0801` |
| 0006 | `29` | `LOAD A, [H]` | `A=66` (`'B'`) |
| 0007 | `02` | `OUT` | надруковано `B` |
| 0008 | `00` | `HALT` | зупинка, `PC=0009` |

Через `run` (це `checks/lab-03.txt`) вивід `AB`, у кінці `H=0801`, `PC=0009`.

## M4 — вказівник хоста проти адреси гостя

`CPU` тримає `Memory* mem` — вказівник **хоста**: це адреса всієї коробки в пам'яті нашого процесу C++. Він потрібен лише C++-коду, щоб знайти масив `data`. А `pc` і `h` — це адреси **гостя**: звичайні числа `0..4095`, індекси в `data`. Програма всередині `ember` бачить і змінює саме їх: `H` можна покласти в пам'ять, надрукувати, збільшити `INCH`. Вони однакові при кожному запуску і на будь-якій машині. Вказівник хоста (`Byte*` усередину `data`) гостю нічого не каже: це 8-байтова адреса процесу, вона щоразу інша, і в 16-бітний регістр вона навіть не влазить. Якщо змішати їх, наприклад записати вказівник хоста в пам'ять `ember` чи тримати `PC` як `Byte*`, програма-гість отримає число, яке після перезапуску або перевиділення пам'яті вказує в нікуди. До того ж `Byte*` можна збільшити за межі масиву, і ніхто цього не помітить. Індекс `uint16_t` ми перевіряємо порівнянням з `MEM_SIZE`, тому `step` ловить вихід за межу до того, як він станеться.

### Навмисний вихід за межу

Тимчасова програма пише на один байт за кінець масиву:

```cpp
Memory mem;
mem.data[MEM_SIZE] = 1;
```

Звіт ASan (головне):

```txt
==288==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7fdc11001020 at pc 0x55fd6c7be432 bp 0x7ffed83fbe40 sp 0x7ffed83fbe30
WRITE of size 1 at 0x7fdc11001020 thread T0
    #0 0x55fd6c7be431 in main oob.cpp:4
...
  This frame has 1 object(s):
    [32, 4128) 'mem' (line 3) <== Memory access at offset 4128 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow oob.cpp:4 in main
```

Три рядки, які мають значення:
1. `stack-buffer-overflow` і `WRITE of size 1` — це запис одного байта за межу масиву на стеку.
2. `#0 ... in main oob.cpp:4` — місце, де це сталося.
3. `'mem' ... overflows this variable` — яку саме змінну переповнено: `mem` займає байти `[32, 4128)`, а запис пішов на 4128.

UBSan окремо повідомив `index 4096 out of bounds for type 'unsigned char [4096]'`.

**Виправлення:** доступ до пам'яті йде тільки через `mem_set`/`mem_get`, які перевіряють `addr >= MEM_SIZE` до запису. `mem_set(mem, MEM_SIZE, 1)` повертає `false` і нічого не пише. Тимчасову програму видалено.
